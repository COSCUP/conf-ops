# Conf-Ops 功能規格架構文件

## 系統簡介

Conf-Ops 是一套以 AI 輔助的研討會/活動專案管理系統，專為重複性高、跨組協作密集的大型活動（如 COSCUP）設計。系統以「任務對話」為核心操作介面，結合 AI 建議與人類決策，讓團隊在累積組織記憶的同時高效完成工作。

## 系統特點與原則

### 核心原則

1. **AI 輔助，人類決策**：AI 永遠不會自主執行任何動作。所有寫入操作（寄信、建立文件、更新資料等）都必須經過人類確認。AI 的角色是建議者，不是執行者。

2. **確定性流程**：AI 建議的觸發、生成、決策、執行、記錄，每一步都是由程式碼明確定義的確定性邏輯，不是 AI 自行決定何時介入。

3. **對話即記錄**：任務對話是所有操作的主要介面，也是完整的審計追蹤。每個動作（誰做了什麼、AI 建議了什麼、人類如何決策）都記錄在對話時間線中。

4. **記憶驅動的持續改善**：系統透過多層級的記憶機制，將每次任務執行的經驗累積下來。記憶作為 AI 的 Skills，讓建議品質隨著組織經驗的累積而持續提升。

### 系統特點

- **模板化與可重複**：任務模板、待辦事項模板，加上專案複製功能，讓每年的活動籌備不必從零開始，直接繼承過去的結構與經驗。

- **多層級記憶繼承**：從帳號到具體任務，記憶沿著繼承鏈層層傳遞。通用經驗存在高層級供所有人參考，特定經驗留在低層級精準應用。

- **內外部參與者統一互動**：成員（Member）與外部聯絡人（Contact）都能透過 Email 自然互動，訊息統一歸入對應任務對話。成員額外可透過 Web 介面操作。

- **跨組協作有權限控管**：各組別預先設定哪些任務模板允許外部建立，待辦事項可關聯到其他組別的任務。透過明確的資料分享工具實現跨組資料傳遞，關聯任務完成後自動回報。

- **結構化資料蒐集**：資料表以任務模板為單位聚合，所有同類型任務的資料一覽無遺，並提供 REST API 供外部系統串接。

- **工具可擴充（MCP）**：核心工具全域可用，其餘內建工具需組織或專案層級啟用設定。組織擁有者與專案擁有者可自行接入第三方 MCP Server，統一格式無縫擴充。

- **不強制線性流程**：待辦事項有模板順序但不強制依序執行，允許臨時支線、跳過步驟、彈性應對實際狀況。

- **隱私優先**：資料表的實際資料不傳送給 AI，AI 僅知道欄位結構並透過佔位符引用。個人資料表為私人所有，可自動填入任務資料表但不對外公開。

- **完整可審計**：所有操作都有跡可循，AI 的 prompt 與回應皆可審查，確保透明與可追溯。

---

> **命名慣例說明：** 本文件使用 JSON/API 層 camelCase 命名（如 `sourceTemplate`、`sourceProject`、`ownerTag`），對應資料庫 snake_case 欄位名（如 `source_template_id`、`source_project_id`、`owner_tag_id`）。

## 一、核心實體 (Entities)

### 1. Account（帳號）

系統的使用者身份，透過 Email 識別。一個帳號可以加入多個組織，並透過組織參與專案。

**登入方式：**
- **Passkey**：基於 WebAuthn 標準的免密碼登入
- **Email Magic Link**：系統寄送一次性登入連結到帳號 Email

> **自動註冊：** 當透過 Magic Link 登入的 Email 尚未對應任何帳號時，系統自動建立新帳號。無論 Email 是否已存在，回應訊息一致（如「Magic Link 已發送至您的 Email」），以防止 Email 列舉攻擊。

**屬性：**
- 名稱 `name`、Email `email`、頭像 `avatar_url`
- **自我介紹 `bio`**：公開的自我介紹文字，可供專案內其他成員查閱
- **語系偏好 `locale`**：使用者偏好語系（VARCHAR，預設 `'zh-TW'`），用於介面語言與 AI 回應語言
- 個人記憶 `memories`：存放個人偏好，如溝通語言、介面習慣等。工作經驗應優先存入組織或專案相關層級，僅純粹個人偏好留在帳號記憶中
- **個人資料表 `profileData`**：私人的結構化資料（如聯絡電話、地址、銀行帳號、飲食偏好等），僅帳號本人可查看與編輯。不對其他成員公開，也不傳送給 AI。欄位為自由新增的 JSON 格式，可手動新增或透過 `saveToProfile` 工具從任務資料中存入。系統程式自動維護個人欄位結構 `profileSchema`（含 `key`、`label`、`description`、`type`），AI 僅接收此結構以判斷對應關係（詳見「隱私系統」）
- 通知偏好設定 `notificationPreferences`
- 所屬組織列表 `organizations`
- 個人待辦清單 `todos`（從所有專案中指派的待辦事項聚合）

帳號可以建立新組織，或加入既有組織。

### 2. Organization（組織）

代表一個團體或社群（如 COSCUP 籌備團隊、開源社群基金會等）。組織是專案的容器，管理跨專案共用的設定與記憶。

**包含：**
- 名稱 `name`、描述 `description`、Logo `logoUrl`
- 成員列表 `members`（帳號在組織中的身份）
- 外部聯絡人列表 `contacts`（組織層級管理，跨專案共用）
- 專案列表 `projects`
- 組織層級的記憶 `memories`（跨專案共用的組織知識與經驗）
- 組織層級的執行工具設定 `toolConfigs`（組織共用的 API 設定，專案可繼承或覆寫）
- **權限設定 `permissionSettings`**

#### 組織層級角色

- **組織擁有者 `org_owner`**：完整管理權限，可管理組織設定、成員、建立專案
- **組織管理者 `org_admin`**：可管理專案、邀請成員，權限由組織擁有者設定
- **組織成員 `org_member`**：可查看組織內的專案，加入專案的權限由各專案控管

#### 加入組織流程

組織擁有者與管理者可透過 Email 邀請成員加入組織：
- **已有帳號**：直接加入組織
- **尚無帳號**：發送邀請信，註冊後自動加入組織

### 3. Project（專案）

屬於一個組織，從空白建立或從同組織內的現有專案複製。

**包含：**
- 名稱 `name`、描述 `description`
- 所屬組織 `organizationId`
- 狀態 `status`：籌備中 `preparing` / 進行中 `active` / 已完成 `completed` / 已封存 `archived`
- 來源專案 `sourceProject`（若為複製建立，參考來源）
- 成員列表 `members`
- 任務列表 `tasks`
- 專案層級的記憶 `memories`
- 執行工具設定 `toolConfigs`（繼承組織設定，可覆寫。基於 MCP 協定）
- **權限設定 `permissionSettings`**（詳見「權限與安全」）

#### 複製專案 Copy Project

僅該專案的現有成員可複製專案（非專案成員無法看到或存取該專案）。複製後的新專案屬於同一組織。複製時，操作者自動成為新專案的擁有者 `owner`。以下為各項目的複製行為：

| 項目 | 複製行為 |
|------|---------|
| 名稱 `name`、描述 `description` | 複製，可在建立時修改 |
| 狀態 `status` | 重設為 `preparing` |
| 來源專案 `sourceProject` | 記錄為來源專案的參考 |
| 成員標籤 `memberTags` | **完整複製**（含名稱、描述、記憶、`externalTaskCreation` 設定） |
| 任務模板 `taskTemplates` | **完整複製**（含待辦事項模板、子待辦事項模板、資料表定義 DataSchema、記憶） |
| 專案記憶 `memories` | **完整複製** |
| 執行工具設定 `toolConfigs` | **完整複製**（含 API Key、連線參數、啟用狀態等所有設定） |
| 權限設定 `permissionSettings` | **完整複製**（含成員標籤的可見性、工具權限等） |
| 成員 `members` | **不複製**，新專案無成員，需重新邀請 |
| 任務 `tasks` | **不複製**，新專案無任務實例 |
| 外部聯絡人 `contacts` | **不複製**（Contact 屬於組織層級，仍可在新專案中使用，但成員標籤指派不複製） |
| 資料表資料 `dataEntries` | **不複製**（僅複製定義，不複製實際資料列） |

> **分階段實作：** 專案複製功能分階段交付。Phase 2 提供基本複製（成員標籤、任務模板含待辦模板與資料表定義、專案記憶、工具設定、權限設定）。Phase 12 擴充深複製能力（含資料快照、歷史資料遷移等進階功能）。

> **典型場景：** 每年 COSCUP 從上一屆專案複製，繼承完整的組織結構（成員標籤、任務模板）與累積的經驗（記憶），但以乾淨的狀態開始新一屆的工作。

### 4. Member（成員）

帳號在特定專案中的身份。一個帳號加入一個專案即成為該專案的一位成員。成員可透過 Web 介面操作，也可以透過 Email 與系統互動（Email 內容會進入對應的任務對話）。

**屬性：**
- 關聯帳號 `accountId`（連結到 Account）
- 所屬專案 `projectId`
- 成員標籤 `tags`（多個）

### 5. Contact（外部聯絡人）

不具備帳號的外部參與者（如贊助商、講者、外部合作對象），僅透過 Email 與系統互動。**Contact 屬於組織層級，同一組織內的所有專案共用。**

**屬性：**
- 名稱 `name`、Email `email`
- 所屬組織 `organizationId`
- 成員標籤 `tags`（可選，如「贊助商」「講者」，各專案可獨立指派）

**建立方式：**
- **手動建立**：成員可在組織中手動建立 Contact，填寫名稱與 Email
- **自動建立**：系統收到未知 Email 來信時，自動建立 Contact 並歸入對應組織

**合併 `merge`：**
- 當同一外部參與者存在多個 Contact 記錄（如不同 Email 或重複建立）時，可將多個 Contact 合併為一個
- 合併後保留一個主要 Contact，其他 Contact 的對話記錄與關聯全部歸併到主要 Contact
- 合併在組織層級操作，影響該組織內所有專案

**跨專案行為：**
- 同一 Contact 可出現在組織內多個專案的任務對話中
- 各專案可為同一 Contact 獨立指派成員標籤
- 複製專案時不複製 Contact 的成員標籤指派（Contact 本身仍在組織中可用）

**與 Member 的共通點：**
- 都可以在任務對話中出現（透過 Email）
- 都可以被指派成員標籤
- 都可以透過 `smtp/sendEmail` 工具寄信互動

**與 Member 的差異：**
- Contact 沒有帳號，不能登入系統、不能在 Web 介面操作、**不能看到任務對話**
- Contact 僅透過執行工具（如 `smtp/sendEmail`）與其互動時才會收到訊息，其回信再進入任務對話
- Contact 不能被指派待辦事項
- Contact 不能確認 AI 建議

> **來源類型區分：** 在任務對話中，Member 透過 Web 介面的發言使用 `member` 來源類型；Contact 無法登入 Web 介面，僅能透過 Email 回信進入對話，使用 `email_inbound` 來源類型，保留完整的郵件來源資訊。透過 `sourceId` 區分身份。

> **跨專案標籤視圖：** `MemberTagAssignment` 包含 `project_id` 欄位，支援同一 Contact 在不同專案擁有不同標籤角色。查詢特定專案下的 Contact 標籤時，API 透過 `GET /api/v1/projects/{projectId}/contacts?includeTags=true` 回傳含專案上下文的標籤列表。

### 6. Member Tag（成員標籤）

代表角色或組別（如：組長、贊助組、資訊組）。屬於專案，可指派給 Member 或 Contact。

**包含：**
- 名稱 `name`、描述 `description`
- 記憶 `memories`（該角色的專屬知識與經驗）
- 任務模板列表 `taskTemplates`（與任務模板為多對多關係）
- **外部建立任務設定 `externalTaskCreation`**：設定哪些自身擁有的任務模板，允許由哪些其他成員標籤的成員建立任務（詳見「跨組協作機制」）

### 7. Task Template（任務模板）

描述一類重複性工作的標準流程。可屬於**多個**成員標籤（多對多關係）。一個成員可擁有多個成員標籤，因此可存取所有相關標籤下的任務模板。

**建立權限：** 任何專案角色皆可建立任務模板。專案擁有者可將任務模板設定屬於任意成員標籤；其他角色（`tag_admin`、`member`）建立的任務模板僅能設定屬於自己所擁有的成員標籤。

**包含：**
- 名稱 `name`、描述 `description`
- **待辦事項模板 `todoTemplates`**：有序的待辦事項清單，每個項目包含：
  - 名稱 `name`、描述 `description`
  - 子待辦事項模板 `subTodoTemplates`（可選，最多一層）
- **資料表定義 `dataSchemas`**：定義任務需蒐集的結構化資料欄位（詳見 Data Sheet）
- 記憶 `memories`（執行此類任務的經驗與注意事項）

### 8. Task（任務）

從任務模板實例化，代表一項具體的工作。雖然任務模板可屬於多個成員標籤，但任務建立時必須明確指定歸屬的成員標籤，以確定該任務的組別歸屬與可見性。

**包含：**
- 名稱 `name`（可自訂，如「與 A 贊助商保持聯絡」）
- 所屬成員標籤 `ownerTag`（任務歸屬的成員標籤，建立時指定）
- 建立者 `createdBy`（建立此任務的成員）
- 來源任務模板 `taskTemplateId`（參考）
- 狀態 `status`：待開始 `pending` / 進行中 `in_progress` / 已完成 `completed` / 已取消 `cancelled`
- **參與人 `participants`**（自動計算，詳見下方）
- **任務對話 `conversation`**（Task Conversation）
- **待辦事項列表 `todos`**（從模板實例化，或臨時建立）
- **資料列 `dataEntries`**（對應任務模板的 Data Sheet，每個任務填寫自己的資料列）
- 記憶 `memories`（繼承自模板 + 任務專屬）
- 關聯任務 `linkedTasks`（從待辦事項的 `linkedTask` 聚合而來，包含本任務待辦所關聯的外部任務，以及其他任務待辦關聯到本任務的反向連結）

#### 參與人 Participants

任務的參與人 `participants` 由系統自動計算，決定了**誰能查看與操作該任務**（包含查看對話、確認 AI 建議、使用執行工具）。參與人包含：

- `ownerTag` 成員標籤下的所有成員
- 在任務對話中被 `@` 標記的成員
- 任務建立者 `createdBy`
- 待辦事項的被指派者 `assignees`

> **Contact 非參與人：** 外部聯絡人（Contact）透過 `email_inbound` 參與任務對話，但**不計入**任務參與人。Contact 無帳號、不能登入系統、不能被指派待辦事項、不能確認 AI 建議，其參與僅限於 Email 往來記錄於對話中。

AI 建議生成後，會顯示給所有參與人，由任一參與人進行決策。

> **參與人計算效能：** 系統使用 `moka` in-memory cache 快取參與人計算結果（key = `task_id`，TTL 1–2 分鐘），任何影響參與人組成的寫入操作（任務指派變更、訊息 @mention、todo assignee 變更）主動 invalidate cache entry。`@mention` 解析結果寫入結構化索引（`messages` 表新增 `mentioned_member_ids UUID[]` 欄位搭配 GIN 索引），避免全文掃描。

#### 狀態轉換規則

- **`pending`（待開始）**：任務剛建立，尚未有實質活動
- **`in_progress`（進行中）**：當任務對話中出現訊息、待辦事項被指派、或有任何操作時，自動轉為進行中
- **`completed`（已完成）**：所有待辦事項皆已完成後，由參與人手動標記為已完成
- **`cancelled`（已取消）**：由參與人手動標記，可從任何狀態轉換

### 9. Task Conversation（任務對話）

任務的完整時間線記錄，是使用者操作的主要介面。

**每則訊息 `Message` 包含：**
- 訊息 ID `messageId`：唯一識別碼，依時間序遞增
- 時間戳 `timestamp`
- 來源類型 `sourceType`：`member`（Member 透過 Web 介面的發言）/ `email_inbound`（Email 來信，Member 或 Contact 的郵件；Contact 僅能透過此來源類型參與對話）/ `ai_suggestion`（AI 建議）/ `tool_execution`（工具執行結果，包含待辦事項變化、資料表變化等）/ `system`（系統事件）
- 來源者 `sourceId`（哪位成員）
- 內容 `content`
- 附件 `attachments`（可選）：檔案列表，每個附件包含 `fileName`、`mimeType`、`fileSize`、`storagePath`。來源包含 Email 附件、成員上傳的檔案等
- 關聯的動作與結果 `actionResult`（如果有）

#### 並行協作與資料同步（CRDT）

系統使用 **CRDT（Conflict-free Replicated Data Types）** 處理多人同時操作的資料一致性問題。所有多人可編輯的協作資料皆透過 CRDT 實現即時同步與自動衝突解決。

**適用範圍：**
- **任務對話**：多人同時留言、確認 AI 建議時，訊息順序透過 CRDT 保證一致性
- **待辦事項**：多人同時修改狀態、指派、截止日期等
- **資料表**：多人同時編輯同一任務的資料列欄位
- **記憶與記憶庫文件**：多人同時編輯記憶內容

**對話的已讀保護 `lastSeenMessageId`：**

CRDT 確保資料一致性，但任務對話額外需要確保使用者在操作前已看到最新內容。所有對話中的寫入操作（送出留言、確認 AI 建議、執行工具等）須附帶 `lastSeenMessageId`：

- **送出時**：客戶端附帶使用者目前看到的最後一則訊息的 `messageId`
- **伺服器驗證**：若 `lastSeenMessageId` 不等於對話中實際的最後一則訊息 ID，拒絕操作並回傳新訊息，要求使用者先閱讀後再操作
- **通過驗證**：操作正常執行並記錄到對話中

> **設計考量：** CRDT 解決的是「多人同時操作不衝突」，`lastSeenMessageId` 解決的是「操作前必須掌握完整資訊」。兩者互補：CRDT 保證技術層面的資料一致性，已讀保護確保業務層面的決策品質。

> **`lastSeenMessageId` 適用範圍：** 所有會在任務對話中產生訊息記錄的寫入操作（包含 `SendMessage`、`UpsertDataEntry`、`UpdateTodo`、`UpdateTaskStatus`、`SuggestionDecision`、`ToolExecute` 等）都須附帶 `lastSeenMessageId`，確保操作者在掌握最新上下文的情況下做出變更。API 層面統一在 request body 中以 `lastSeenMessageId` 欄位攜帶（UUID 格式），所有相關 Request Schema 皆包含此必填欄位。

> **`lastSeenMessageId` vs `last_read_message_id`：** 系統使用兩個獨立的已讀追蹤機制：`lastSeenMessageId` 是 API request body 中的必填欄位，用於寫入操作前的已讀保護（確保操作者已看到最新訊息）；`last_read_message_id` 儲存於 `conversation_states` 表，用於 UI 層的未讀計數追蹤（標記使用者已讀到哪則訊息）。兩者獨立運作，互不影響。

> **CRDT 與 REST 共存邊界：** CRDT（WebSocket Binary）負責即時協作同步（多人同時編輯 content、status 等），REST API（PUT/PATCH）用於離線或非即時場景（如 AI 工具執行結果寫入、外部 API 更新）。REST 寫入時，後端先將變更轉換為 CRDT 操作再合併至操作日誌，確保物化狀態始終由 CRDT 日誌驅動，REST 不直接覆寫物化表。

> **斷線重連位置追蹤：** 系統透過 `last_seen_positions` 表追蹤每位使用者的 Yjs clock position，記錄使用者最後同步的 CRDT 狀態位置。當使用者斷線後重新連線時，系統僅需傳送自該 position 之後的差異更新，而非完整狀態，大幅降低重連時的資料傳輸量。

> **API 分層規則：** 內部 API（使用者操作、前端呼叫）使用 `/api/v1/` 前綴，由 JWT Bearer Token 認證；外部資料 API（第三方系統串接）使用 `/external/v1/` 前綴，由專案層級 API Key（`X-API-Key` header）認證。兩者在 OpenAPI 規格中共存但路由與認證策略明確分離。

### 10. Todo（待辦事項）

**屬性：**
- 標題 `title`、描述 `description`
- 截止日期 `dueDate`
- 指派成員 `assignees`（一或多位）
- 狀態 `status`：未完成 `open` / 已完成 `completed`
- 類型 `type`：`template`（從待辦事項模板產生）/ `ad_hoc`（臨時建立）
- 所屬任務 `taskId`
- 父待辦事項 `parentTodoId`（可選，最多一層子待辦）
- 子待辦事項 `subTodos`（可選）
- 關聯任務 `linkedTask`（可選，此待辦對應的另一個任務。用於跨組協作：待辦事項可關聯一個在其他組別建立的任務，該任務完成時來源任務對話會收到通知。詳見「跨組協作機制」）

子待辦事項全部完成時，不會自動完成父待辦事項，需由成員手動確認。

**操作權限：** 任務的所有參與人（`participants`）皆可操作待辦事項（建立、修改、標記完成、指派等），不限於被指派者。

變化（建立、修改、完成）自動記錄到任務對話。

### 11. Data Sheet（資料表）

以任務模板為單位的結構化資料蒐集機制。同一任務模板下的所有任務共享相同的資料表結構，每個任務各自填寫一筆資料列，形成跨任務的聚合資料集。

#### 資料表定義 Data Schema

定義於任務模板中，描述資料欄位結構：

```
DataSchema {
  name: 資料表名稱（如「贊助商資訊」）
  fields: [
    {
      key: 欄位鍵名
      label: 欄位顯示名稱
      description: 欄位說明（描述此欄位的用途、預期內容、填寫範例等，供 AI 判斷如何填入）
      type: 欄位類型（見下方）
      required: 是否必填
      constraints: 欄位限制（依類型不同，見下方）
    }
  ]
}
```

**欄位類型 `type` 與限制 `constraints`：**

| 類型 | 說明 | 可設定限制 |
|------|------|-----------|
| `single_line_text` | 一行文字 | `maxLength` 最大字數 |
| `multi_line_text` | 多行文字 | `maxLength` 最大字數、`maxLines` 最大行數 |
| `number` | 數字 | `min` 最小值、`max` 最大值、`decimal` 是否允許小數 |
| `date` | 日期 | `minDate` 最早日期、`maxDate` 最晚日期 |
| `email` | Email 地址 | — |
| `url` | 網址 | — |
| `select` | 單選 | `options` 選項列表 |
| `boolean` | 布林值 | — |
| `image` | 上傳圖片 | `maxFileSize` 最大檔案大小、`accept` 允許的圖片格式（如 `jpg, png`） |
| `file` | 上傳檔案 | `maxFileSize` 最大檔案大小、`accept` 允許的檔案格式 |

#### 資料表實例 Data Sheet

屬於任務模板，聚合該模板下所有任務的資料：

**屬性：**
- 來源定義 `schemaRef`（參考 DataSchema）
- 所屬任務模板 `taskTemplateId`
- 資料列 `entries`：每筆資料關聯一個任務 `taskId`，包含各欄位的值

每個任務在對話介面中可查看與編輯自己的資料列，任務模板層級可查看所有任務的聚合資料。

#### 特性

- **對話中可見**：資料變化（新增、修改、刪除）透過執行工具操作，自動以 `tool_execution` 類型記錄到任務對話，以區塊形式呈現
- **執行工具可操作**：透過 `upsertDataEntry` 工具新增或修改資料
- **跨任務聚合**：以任務模板為單位，彙整所有任務的資料列，方便總覽與統計（如所有贊助商的聯絡狀態一覽）
- **跨任務資料分享**：透過 `shareDataToTask` 工具，可將指定欄位的資料複製到其他任務的資料表中，並建立來源關聯。來源資料變更時通知目標任務（詳見「跨組協作機制」）。`ShareDataToTaskRequest` 須指定 `targetSchemaId`，明確資料要分享到目標任務的哪一個 DataSchema；若目標任務僅有單一 Schema，前端可自動填入
- **外部 API 存取**：提供 REST API 端點，可依專案、任務模板、任務查詢與聚合資料，供外部系統串接使用
- **AI 上下文（僅結構）**：基於隱私設計，AI 僅接收資料表的欄位結構（Schema），不接收實際資料值。AI 透過佔位符語法引用欄位，由系統在執行時帶入實際資料（詳見「隱私系統」）

> **變更歷史追蹤：** `data_entries` 的變更透過審計日誌（`audit_logs`）追蹤，不另建獨立的版本歷史表。每次資料修改皆記錄操作者、變更欄位與前後值至審計日誌，提供完整的變更追溯能力。

### 12. Execution Tool（執行工具）

系統提供的可執行動作，AI 或人類都可以觸發。

**所有工具統一採用 MCP 格式**（工具定義、參數結構、回傳格式皆遵循 MCP 協定標準），無論是內建工具或第三方工具，人類操作或 AI 建議，都使用相同的介面格式。這簡化了實作，也確保第三方 MCP Server 能無縫接入。

差異僅在通訊方式：
- **內建工具**：直接呼叫系統程式碼執行，不經過 STDIO 或 SSE 等傳輸層
- **第三方工具**：透過 MCP 協定標準的傳輸方式（STDIO / SSE）與外部 MCP Server 通訊

工具分為三層：核心工具（系統內建、全域可用）、可設定內建工具（需專案層級啟用）、第三方工具（專案擁有者自行接入）。所有工具再依操作性質區分為寫入工具（需人類確認）與查詢工具（不需確認）。

#### 核心工具（全域可用）

與系統本身互動的基礎工具，所有專案、所有成員皆可使用，不需額外啟用或設定。AI 僅建議，人類決策後由系統執行。

**寫入（需人類確認）：**

- **建立任務 `createTask`**：從任務模板建立新任務。可建立自身成員標籤的任務，也可建立其他組別允許外部建立的任務（詳見「跨組協作機制」）。可選擇關聯到當前任務的某個待辦事項 `parentTodoId`，建立跨組任務連結
- **建立待辦事項 `createTodo`**：在任務中新增待辦
- **更新待辦事項 `updateTodo`**：更新待辦事項的狀態（標記完成等）、指派成員、截止日期、描述等
- **新增/更新資料 `upsertDataEntry`**：新增或修改資料表中的資料列。AI 使用佔位符語法指定欄位值，系統在執行前帶入實際資料供人類確認
- **分享資料到其他任務 `shareDataToTask`**：將當前任務資料表中指定欄位的資料，複製到目標任務的資料表中。目標任務需有對應的欄位可接收。複製時建立來源關聯 `sourceLink`，當來源資料變更時，目標任務對話會收到 `system` 通知並觸發 `source_data_changed` AI Pipeline 事件，AI 自動生成 SuggestionGroup 建議同步更新相關欄位，由目標任務成員審核決策
- **儲存到個人資料表 `saveToProfile`**：將任務資料表中的指定欄位值存入當前操作成員的個人資料表。若 `profileSchema` 中已存在該 `key` 的欄位結構，則不需提供結構參數，直接存入值即可；若為新欄位，參數中須包含欄位結構資訊（`label`、`description`、`type`），來源是任務資料表欄位時可直接從 DataSchema 帶入，若缺少則工具回傳錯誤不執行，由 AI 建議補上或人類手動補填後重新執行。系統程式以固定邏輯維護 `profileSchema`。AI 可在偵測到成員重複填寫相同個人資料時建議使用
- **建立/更新記憶 `upsertMemory`**：新增或修改記憶條目。可同時指定 `libraryRef` 參考記憶庫文件
- **建立/更新記憶庫文件 `upsertLibraryDocument`**：新增或修改記憶庫中的文件（如 SOP、範本、詳細指南等）


**查詢（不需人類確認）：**

- **查詢記憶 `queryMemories`**：搜尋各層級的記憶條目（摘要）
- **查詢記憶庫文件 `queryLibraryDocument`**：讀取記憶庫文件的完整內容，AI 在判斷記憶摘要與當前任務相關後，按需查詢詳細內容
- **查詢資料表結構 `queryDataSchema`**：查詢任務或任務模板的資料表欄位結構（Schema），不回傳實際資料值（隱私設計）
- **查詢待辦事項 `queryTodos`**：查詢任務的待辦事項狀態與進度
- **查詢成員資訊 `queryMembers`**：查詢專案成員、標籤與聯絡資訊

> **注意：** 任務對話歷史預設包含在 AI 的上下文中，不需要額外的查詢工具。

#### 可設定內建工具（需專案層級啟用）

系統內建但需要外部服務設定的工具，須由專案擁有者在專案中明確啟用並設定後才可使用：

- **SMTP 寄送信件 `smtp/sendEmail`**：透過 SMTP 發送 Email。支援多條 Email Thread 管理（詳見下方）。**設定：** SMTP 主機、連接埠、帳號密碼、寄件者地址

  #### Email Thread 機制

  每個任務可維護**多條 Email Thread**，每條 Thread 代表一組獨立的 Email 往來脈絡。

  **Thread 資料結構：**
  - `threadId`：系統內部識別碼
  - `subject`：Email 主旨
  - `participants`：此 Thread 的收件對象（Email 地址列表）
  - `messageIds`：此 Thread 中所有 Email 的 `Message-ID` 列表，用於維持回覆鏈

  **寄信時的 Thread 處理：**
  - AI 建議 `smtp/sendEmail` 時，根據收件人與對話上下文決定：回覆既有 Thread（參數帶 `threadId`）或建立新 Thread（不帶 `threadId`）
  - 回覆既有 Thread 時，系統自動設定 Email Header（`In-Reply-To`、`References`），讓收件者的信箱正確歸入同一對話串
  - 建立新 Thread 時，系統產生新的 `threadId` 並記錄首封信的 `Message-ID`
  - 同一 Thread 中即使收件者/寄件者變更（如窗口轉接）仍維持同一串

  **收信時的 Thread 匹配：**
  1. **優先**：依據 Email Header（`In-Reply-To`、`References`）匹配到既有 Thread
  2. **次要**：依據寄件者 Email + 主旨關鍵字啟發式匹配
  3. **無法匹配**：歸入任務的未分類信件，或專案的未分類收件匣

  > **範例：** 「與 X 公司聯絡」任務中，與 X 公司贊助商的往來是 Thread A（主旨：COSCUP 2026 贊助合作），向 OCF 確認款項是 Thread B（主旨：X 公司匯款確認）。兩條 Thread 各自獨立，對外部參與者來說就是正常的 Email 回覆鏈
- **HackMD 建立共筆文件 `hackmd/createDocument`**：透過 HackMD API 建立共筆文件。**設定：** HackMD API Key、預設範本
- **Google Meet 建立視訊會議 `googleMeet/createMeeting`**：透過 Google Meet API 建立會議。**設定：** Google API 憑證
- **Google Docs 建立會議紀錄 `googleDocs/createMeetingNote`**：透過 Google Docs API 建立結構化的會議記錄文件。**設定：** Google API 憑證

以上皆為寫入工具，需人類確認後執行。

#### 第三方工具（專案擁有者自行接入）

專案擁有者可在專案中新增第三方 MCP Server，因統一使用 MCP 格式，可直接接入無需額外的格式轉換。

**工具設定層級：** 組織 `Organization` → 專案 `Project`（專案繼承組織設定，可覆寫。複製專案時繼承來源設定）

**設定內容：** 各工具的 API Key、連線參數、啟用/停用 `enabled`

### 13. Memory（記憶）

對應 AI Agent 概念中的 Skills，是 AI 生成建議時的知識與經驗基礎。

- **內容 `content`：** 簡短的文字摘要，描述這條記憶的重點。保持精簡，避免記憶條目膨脹
- **記憶庫參考 `libraryRef`：**（可選）參考記憶庫中的文件 ID，提供完整的詳細內容。當記憶需要附帶較長的說明、範本、SOP 等內容時，將完整內容存入記憶庫，記憶條目僅保留摘要與參考連結
- **作用域層級 `scope`：** 帳號 `account` / 組織 `organization` / 專案 `project` / 成員標籤 `member_tag` / 任務模板 `task_template` / 任務 `task`
- **來源 `source`：** `manual`（人工建立）/ `auto_extracted`（從任務執行過程中 AI 提取，需人工確認）
- **用途：**
  - 作為 AI 生成建議時的上下文
  - 作為成員的參考知識庫（可在 Web 介面瀏覽）
- **記憶繼承 `inheritance`：** 下層自動繼承上層記憶，AI 生成建議時會組合所有相關層級的記憶

#### 記憶庫 Memory Library

每個擁有記憶的作用域層級（帳號、組織、專案、成員標籤、任務模板、任務）各自擁有一個記憶庫，用於存放記憶條目參考的完整文件。

**記憶庫文件 `LibraryDocument` 屬性：**
- 文件 ID `documentId`
- 標題 `title`
- 內容 `content`：完整的文字內容（如 SOP、信件範本、會議紀錄範本、詳細操作指南等）
- 版本歷史 `versionHistory`

**運作方式：**
- 記憶條目的 `content` 保持簡短摘要（如「初次聯絡信範本，參考記憶庫」），透過 `libraryRef` 指向記憶庫文件取得完整內容
- AI 生成建議時，先讀取繼承鏈上所有記憶條目的摘要，再依需要透過查詢工具讀取相關的記憶庫文件完整內容
- 記憶庫文件可獨立於記憶條目被瀏覽與編輯
- 一份記憶庫文件可被多條記憶條目參考

> **設計目的：** 記憶條目保持精簡摘要，AI 能快速掃描所有記憶判斷相關性；需要詳細內容時再查詢記憶庫，避免大量完整內容塞入上下文造成記憶膨脹。

## 二、核心機制

### 1. AI-Human 協作迴圈 `AIHumanLoop`（最核心機制）

這是整個系統的核心，流程是**確定性的程式碼邏輯**，不是 AI 自行決定：

```
觸發事件 (Trigger) → AI 生成建議 (Suggestion) → 人類決策 (Decision) → 執行 (Execution) → 記錄 (Record)
```

> **事件持久化：** 觸發事件以 PostgreSQL `ai_pipeline_events` 表持久化，包含 retry 與 timeout 機制。Tokio worker 從持久化佇列消費事件，服務重啟時自動恢復未處理的事件。詳見 `docs/system/04-ai-pipeline.md` §7.3。

#### 觸發事件（Trigger）

以下事件會觸發 AI 生成建議，由程式碼明確定義：

1. **任務建立 `task_created`**：從任務模板建立任務時
2. **待辦事項完成 `todo_completed`**：某個待辦事項被標記完成時
3. **成員發送訊息 `message_sent`**：任何成員（內部或外部）在對話中發送訊息時，包含內部成員留言、外部成員 Email 來信、以及透過 Webhook 轉入的外部成員訊息
4. **工具執行錯誤 `tool_error`**：執行工具回傳錯誤時（如參數缺失、權限不足、外部服務失敗等），觸發 AI 建議協助修正或提供替代方案
5. **來源資料變更 `source_data_changed`**：透過 `shareDataToTask` 分享到本任務的資料，其來源任務的對應欄位發生變更時。系統在目標任務對話中新增 `system` 訊息通知變更內容（如「來源任務『與 X 公司聯絡』的公司簡介欄位已更新」），並觸發 AI 建議，由目標任務參與人決定是否同步更新

> **注意：** 工具執行成功不獨立觸發 AI 建議。執行結果作為 `tool_execution` 訊息記錄到對話中，會在下一次觸發事件（如 `todo_completed`、`message_sent`）時納入 AI 的上下文。

> **注意：** 定時提醒（如待辦事項接近/超過截止日期）屬於獨立的提醒系統 `ReminderSystem`，不經過 AI 建議流程。詳見下方「提醒系統」。

#### AI 建議（Suggestion）

AI 生成建議時，以下資訊預設已在上下文中：任務對話歷史、當前操作帳號的個人記憶 `account.memories`、成員在該專案中的成員標籤列表 `member.tags`。此外，AI 會透過查詢工具（不需人類確認）自動蒐集額外上下文（各層級記憶、資料表結構、待辦進度等）。

> **隱私設計：** AI 不接收資料表的實際資料值（包含個人資料表與任務資料表），僅接收欄位結構（Schema）。AI 透過佔位符語法（如 `{{profile.phone}}`、`{{data.companyName}}`）引用欄位值，系統在工具執行前將佔位符替換為實際資料，供人類確認後執行。詳見「隱私系統」。

AI 建議是結構化的，不是自由文字。每次觸發可產生**一至多個建議（最多 5 個）**，每個建議都對應一個寫入工具（需人類確認）的呼叫：

```
SuggestionGroup {
  suggestions: Suggestion[]  // 1~5 個建議
}

Suggestion {
  summary: 人類可讀的簡要說明
  tool: 建議使用的執行工具名稱（對應 MCP tool call 的 name）
  parameters: 工具的參數（對應 MCP tool call 的 arguments，格式與 MCP 一致）
  reasoning: AI 的推理說明
  context_used: 使用了哪些記憶（Skills）和上下文
}
```

#### 人類決策（Decision）

對每個 AI 建議，人類可**個別**做出決策（由程式碼定義，不是 AI 決定的）：

- **採納 `accept`**：直接執行建議的動作
- **修改後採納 `modify_and_accept`**：修改參數後執行
- **拒絕 `reject`**：不執行，可附帶原因
- **要求重新建議 `re_suggest`**：給 AI 額外指示，重新生成建議
- **手動操作 `manual`**：不用 AI 建議，自己選擇執行工具和參數

#### 執行（Execution）

- 工具執行由系統程式碼處理，不是 AI 直接操作
- 執行前顯示完整參數供人類確認
- 執行結果記錄到任務對話

#### 記錄（Record）

每個步驟都完整記錄：觸發原因 `trigger` → AI 建議內容 `suggestion` → 人類決策 `decision` → 執行結果 `result`

### 2. 通知與提醒系統 `NotificationSystem`

統一處理系統中所有通知，獨立於 AI 建議流程。系統不提供獨立的「通知成員」工具，所有通知皆由明確的動作或規則觸發。

#### 即時通知觸發條件

- 待辦事項被指派 `todo_assigned`：指派成員 `assignees` 變更時通知被指派者
- 對話中標記成員 `member_mentioned`：在任務對話中使用 `@member` 標記
- 對話中標記成員標籤 `tag_mentioned`：在任務對話中使用 `@tag` 標記，通知該標籤下所有成員

#### 定時提醒觸發條件

- 待辦事項接近截止日期 `due_date_approaching`（可設定提前天數）
- 待辦事項超過截止日期 `due_date_overdue`
- 待辦事項長時間未推進 `todo_stale`

#### 提醒排程完整流程

提醒系統的執行由 Worker 負責，完整流程如下：

1. **排程觸發**：Worker 以每分鐘為週期執行排程器
2. **查詢符合條件提醒**：查詢 `scheduled_reminders` 表中 `trigger_at <= NOW() AND fired = false` 的記錄
3. **狀態檢查**：對每筆提醒檢查關聯的待辦事項狀態，若已完成或已刪除則跳過（僅標記 `fired`，不產生通知）
4. **產生通知**：為仍處於 `open` 狀態的待辦事項產生 `Notification` 記錄
5. **多管道發送**：依接收者的 `notificationPreferences` 透過 in_app、Web Push、Email 等管道投遞通知
6. **更新提醒記錄**：將 `fired` 設為 `true`、`fired_at` 設為當前時間、`notification_id` 設為產生的通知 ID

#### 通知方式

- 系統內通知（通知中心、Web Push）
- Email 通知
- 依成員通知偏好設定 `notificationPreferences` 決定通知管道

#### 與 AI 建議的區別

- 通知與提醒系統是**確定性的規則引擎**，不涉及 AI 生成內容
- 僅通知相關成員，不產生 Suggestion
- 成員收到通知後，可自行決定是否進入任務對話請求 AI 建議

### 3. 記憶系統 `MemorySystem`

#### 記憶繼承鏈 Memory Inheritance Chain

AI 生成建議時，沿著任務的 `ownerTag` 所在的繼承鏈收集所有相關記憶：

```
帳號記憶 (Account) ──────────────────────────────────────────────────────────────┐
組織記憶 (Organization) → 專案記憶 (Project) → ownerTag 記憶 (MemberTag) → 任務模板記憶 (TaskTemplate) → 任務記憶 (Task)
```

- 繼承鏈依據任務的 `ownerTag`（歸屬成員標籤）決定，而非操作者的所有標籤
- 帳號記憶為當前操作帳號的個人記憶，獨立於 ownerTag 繼承鏈
- 組織記憶為跨專案共用的組織級知識（如組織文化、通用 SOP、歷屆共通經驗等）
- AI 先讀取繼承鏈上所有層級的記憶摘要（`content`），判斷相關性後，再透過 `queryLibraryDocument` 查詢相關記憶庫文件的完整內容

> **記憶存放原則：** 跨專案通用的組織知識（如組織文化、歷屆共通 SOP）存入組織層級。專案特定的工作經驗存入專案相關層級（專案/成員標籤/任務模板）。僅純粹個人偏好（如「請用臺灣正體中文與我溝通」）留在帳號記憶中。

#### 自動記憶提取 Auto Extraction

- 任務完成時，AI 可以從對話歷史中提取經驗教訓
- 提取結果標記為 `auto_extracted` 來源，必須經人類確認後才會存入記憶
- 完整流程：AI 分析對話歷史 → 生成記憶提取建議（`upsertMemory` 工具呼叫，標記 `source: auto_extracted`）→ 人類審核（可編輯、拒絕或補充）→ 確認後存入對應層級的記憶
- 人類可以編輯、拒絕或補充 AI 提取的記憶

#### 記憶可見性

- 成員可在 Web 介面瀏覽所有層級的記憶
- 記憶有版本歷史 `versionHistory`，可追蹤修改

### 4. 跨組協作機制 `CrossTeamCollaboration`

當一個組別需要另一個組別協助時，透過**待辦事項關聯任務**的方式實現。來源任務的一個待辦事項可以關聯到在其他組別建立的新任務，由目標組別獨立執行，完成後自動回報。

#### 前置設定：外部建立任務權限

各成員標籤可預先設定 `externalTaskCreation`，控制自己擁有的任務模板是否允許其他組別建立任務：

```
externalTaskCreation: [
  {
    taskTemplateId: "社群貼文發佈"
    allowedFromTags: "*"  // "*" 表示允許所有其他成員標籤，也可指定如 ["贊助組", "議程組"]
  }
]
```

- `allowedFromTags` 設為 `"*"` 時，所有其他成員標籤的成員皆可建立任務（預設推薦）
- `allowedFromTags` 設為標籤名稱陣列時，僅列出的標籤可建立任務
- 未列入設定的任務模板，僅該標籤自身成員可建立任務

#### 流程

```
來源任務待辦 → createTask 建立其他組別的任務 → 待辦關聯新任務 → 目標組別獨立作業 → 完成後回報來源任務
```

1. **建立關聯任務**：來源任務成員使用 `createTask` 工具，從目標組別允許外部建立的任務模板建立新任務，並指定關聯到當前任務的某個待辦事項
2. **自動連結**：新任務與來源任務的待辦事項建立關聯（`todo.linkedTask`），來源任務的 `linkedTasks` 同步更新。目標組別相關成員收到通知
3. **資料傳遞**：來源任務成員使用 `shareDataToTask` 工具，將指定欄位的資料複製到關聯任務的資料表中，供目標組別使用
4. **獨立作業**：目標組別在自己的任務對話中獨立作業，擁有自己的資料表
5. **中間進度回報**：關聯任務的參與人可在對話中回報中間進度，來源任務對話會收到 `system` 類型的進度通知，但**不會**關閉來源待辦事項
6. **完成回報**：關聯任務完成（狀態轉為 `completed`）時，來源任務對話中自動新增 `system` 類型訊息通知，觸發 AI 建議流程。**僅當關聯任務完成時**，來源待辦事項才可被標記為完成

#### 資料傳遞規則

- 資料表不會自動共享，需透過 `shareDataToTask` 工具明確複製指定欄位到目標任務
- 複製時建立來源關聯 `sourceLink`，記錄資料來自哪個任務的哪些欄位
- 來源資料變更時，目標任務對話收到 `system` 通知（如「來源任務『與 X 公司聯絡』的公司簡介欄位已更新」），同時觸發 `source_data_changed` AI Pipeline 事件，AI 自動生成 SuggestionGroup 建議同步更新相關欄位，由目標成員審核決策
- 各任務的資料表互相獨立，目標組別可在複製資料的基礎上自行修改
- 每次資料分享都記錄在雙方的任務對話中（`tool_execution`）

#### 在任務對話中的呈現

- 來源任務：`tool_execution` 記錄任務建立與待辦關聯、資料分享 → `system` 記錄關聯任務狀態變化與完成
- 目標任務：`tool_execution` 記錄接收到的資料分享，對話中顯示來源任務參考

### 5. 外部整合 `ExternalIntegration`

#### Email 收信整合

系統透過 Mailing List 接收信件。Member（成員）和 Contact（外部聯絡人）的來信都會進入任務對話。收到 Email 後：

1. 系統解析寄件者 `sender`、主旨 `subject`、內容 `body`、附件 `attachments`
2. 判斷來源身份：
   - **Member 來信**：寄件者 Email 匹配到專案中的成員（透過帳號 Email），以該成員身份記錄
   - **Contact 來信**：寄件者 Email 匹配到專案中的外部聯絡人，或自動建立新的 Contact
   - **成員轉寄**：寄件者為成員，但信件內容為外部來信轉寄。系統解析原始寄件者，以 Contact 身份記錄（而非轉寄者）
3. 嘗試匹配到對應的任務：優先依據 Email Header（`In-Reply-To`、`References`）匹配到既有 Thread 所屬的任務；次要依據寄件者身份、主旨關鍵字啟發式匹配
4. 在匹配的任務對話中新增 `email_inbound` 類型的訊息，附件以 `attachments` 儲存於訊息中（詳見下方「Email 附件處理」）
5. 觸發 AI 建議流程
6. 若無法匹配，歸入專案的未分類收件匣 `unassignedInbox`，等待成員分配
   > **注意**：`unassignedInbox` 是一個**虛擬概念**，不對應獨立的資料表。它是一個查詢結果——篩選 `email_threads` 中 `task_id IS NULL` 的信件串，即尚未關聯到任何任務的 Email。成員可從此列表中將信件手動分配到合適的任務。

#### Email 互動方式

Member 和 Contact 都可透過 Email 與任務對話互動：

- **回覆（CC Mailing List）**：回覆時 CC Mailing List，內容自動歸入對應任務對話
- **回覆（未 CC Mailing List）**：僅回覆給個人，收信者將信件轉寄至 Mailing List，系統以原始寄件者身份記錄
- **主動來信**：系統根據寄件者與主旨匹配任務
- 成員可在任務對話中透過 `smtp/sendEmail` 工具寄信給 Contact 或其他 Member，維持雙向溝通

#### Email 附件處理

Email 來信的附件會儲存於系統中，並作為任務對話訊息的一部分，供成員查看與 AI 建議參考。

**處理流程：**
1. 系統接收 Email 附件，儲存檔案並記錄於訊息的 `attachments` 中
2. 每個附件包含：檔案名稱 `fileName`、檔案類型 `mimeType`、檔案大小 `fileSize`、儲存路徑 `storagePath`
3. AI 可依據附件的檔案名稱與類型判斷用途，建議將附件存入資料表對應欄位（如 `image`、`file` 類型欄位）
4. 成員確認後，透過 `upsertDataEntry` 工具將附件關聯到資料表欄位

**AI 上下文：** AI 接收附件的metadata（檔案名稱、類型、大小），不接收檔案內容本身。AI 根據 metadata 與對話上下文判斷附件用途並生成建議。

> **範例：** 贊助商回信附上公司 Logo 圖檔與合約 PDF。AI 根據檔案名稱與類型，建議將 Logo 存入資料表的「公司 Logo」欄位、合約存入「合約文件」欄位。成員確認後執行。

#### Email Thread 手動修正

當系統自動匹配的 Email Thread 歸屬有誤時（如主旨相似但實際屬於不同任務），成員可透過 `POST /api/v1/email/threads/{threadId}/reassign` 將 Thread 重新歸屬到正確的任務，或將未分類收件匣中的信件關聯至指定任務。操作會在相關任務對話中產生 `system` 類型訊息，記錄重新歸屬的操作。

#### Webhook/API 整合

- 專案可配置 Webhook 端點 `webhookEndpoints`
- 外部系統推送事件 → 路由到對應任務 → 新增對話記錄 → 觸發 AI 建議
- 提供 REST API 供外部系統查詢和操作

### 6. 隱私系統 `PrivacySystem`

確保資料表中的實際資料不直接傳送給 AI，保護個人隱私與敏感業務資料。

#### 核心原則

AI **僅接收資料表的欄位結構（Schema）**，不接收實際資料值。Schema 中的 `description` 欄位說明提供 AI 足夠的語意資訊來判斷欄位用途與填入方式。這適用於：
- 個人資料表 `profileData`：欄位結構 `profileSchema` 由帳號本人自由維護，可隨時新增欄位
- 任務資料表 `dataEntries`：欄位結構 `dataSchemas` 由任務模板定義

#### 對話歷史中的資料遮蔽

任務對話歷史作為 AI 的上下文時，系統會**自動遮蔽**對話中出現的實際資料值。遮蔽僅影響傳送給 AI 的上下文，人類在 Web 介面查看對話時可看到完整資料。

**遮蔽規則（依訊息類型）：**

| 訊息類型 | 遮蔽規則 |
|---------|---------|
| `tool_execution`（工具執行結果） | 資料表欄位的實際值替換為佔位符（如 `{{data.companyName}}`）。附件內容不傳送，僅保留 metadata |
| `member`（成員/外部來信） | 比對已知的個人資料表欄位值（`profileData`）與資料表欄位值（`dataEntries`），匹配到的內容替換為對應佔位符。Email 附件內容不傳送，僅保留 metadata |
| `ai_suggestion`（AI 建議） | 建議中的佔位符保持原樣（本身已是遮蔽狀態）。人類修改後採納的實際值，回寫對話記錄時進行遮蔽 |
| `system`（系統事件） | 系統訊息中引用的資料表欄位值替換為佔位符 |

**遮蔽執行方式：**
1. **結構化資料遮蔽**：`tool_execution` 與 `system` 訊息中的資料表欄位值，系統可直接透過欄位 key 精確替換為 `{{data.<fieldKey>}}` 或 `{{profile.<fieldKey>}}`
2. **自由文字遮蔽**：`member` 訊息為自由文字，系統以已知的資料表欄位值與個人資料表欄位值為比對字典，進行字串匹配替換。未匹配到的內容保持原樣——一旦該資料後續被存入資料表，後續傳給 AI 的對話歷史中即可透過結構化遮蔽處理

> **設計考量：** 自由文字中首次出現的未知敏感資料無法即時遮蔽，但一旦該資料透過工具存入資料表或個人資料表，即納入比對字典，後續傳給 AI 的對話歷史會自動遮蔽。核心保護仍依賴「AI 不接收資料表實際值」的結構化隔離設計。

#### 佔位符語法 Placeholder Syntax

AI 在生成建議時，使用佔位符引用資料欄位值：

```
{{profile.<fieldKey>}}     // 引用當前成員的個人資料表欄位
{{data.<fieldKey>}}        // 引用當前任務的資料表欄位
```

**範例：** AI 建議寄送 Email 時，信件內容可能為：
```
親愛的 {{data.contactName}} 您好，

感謝 {{data.companyName}} 確認贊助，金額為 {{data.amount}}。
如有疑問請聯繫承辦人，電話：{{profile.phone}}。
```

#### 執行流程

1. AI 生成包含佔位符的建議參數
2. 系統將佔位符替換為實際資料值
3. 替換後的完整內容顯示給人類確認
4. 人類確認後執行

人類在確認步驟中可以看到替換後的實際資料，確保內容正確。

#### 佔位符預覽與解析

前端可透過 `POST /api/v1/ai/resolve-placeholders` 端點預覽佔位符的解析結果。前端傳入含佔位符的參數（如信件草稿），後端替換為真實值後回傳供人類審核。此設計確保前端不需持有全量敏感資料，同時讓人類在採納 AI 建議前可預覽真實內容。此端點也用於前端顯示 AI 建議卡片時的即時預覽。

#### 個人資料表的自動填入與累積

- **自動填入**：AI 在任何寫入工具的參數中，都可使用 `{{profile.<fieldKey>}}` 語法引用個人資料表欄位。例如在 `upsertDataEntry` 建議中，AI 可將任務資料表欄位值設為 `{{profile.phone}}`，系統在執行前帶入實際值。不需要獨立的填入工具
- **自動累積**：AI 偵測到成員在不同任務中重複手動填寫相同個人資料時，建議使用 `saveToProfile` 工具，將資料存入個人資料表供未來自動填入
- **欄位結構自動維護**：`saveToProfile` 執行時，系統程式以固定邏輯維護 `profileSchema`。若該 `key` 已存在於 `profileSchema` 中，直接更新值，不需提供結構參數；若為新欄位，需從執行參數中取得結構資訊（`label`、`description`、`type`，如來源為任務資料表欄位則自動帶入），缺少時工具回傳錯誤不執行，錯誤訊息記錄到對話中，由 AI 建議補上或人類手動補填後重新執行。API 層面，`saveToProfile` 的欄位結構資訊透過通用工具執行端點（`POST /projects/{projectId}/tools/{toolName}/execute`）的 `parameters` JSONB 傳遞，`AccountResponse.profileSchema` 始終反映最新狀態
- 所有操作都需經人類確認後執行

### 7. 審計追蹤 `AuditTrail`

所有操作都記錄完整的審計日誌 `AuditLog`：

- 誰 `actor`（成員/AI/系統）
- 做了什麼 `action`（動作類型與詳細內容）
- 什麼時候 `timestamp`
- 在哪個上下文 `context`（專案/任務）
- 結果是什麼 `result`

任務對話本身就是該任務的審計記錄，系統層級另有全局審計日誌。

## 四、權限與安全

### 權限模型 Permission Model

權限分為組織層級與專案層級。組織層級控管成員與專案的管理權限，專案層級依靠成員標籤設計細部權限。

#### 組織層級角色

- **組織擁有者 `org_owner`**：完整管理權限，可管理組織設定、成員、建立專案、設定組織層級工具與記憶
- **組織管理者 `org_admin`**：可建立專案、管理組織成員，權限範圍由組織擁有者設定
- **組織成員 `org_member`**：可查看組織內專案列表，加入專案需由專案擁有者或標籤管理者邀請

#### 專案層級角色

- **專案擁有者 `owner`**：完整管理權限，可設定權限規則、管理所有成員與標籤。可設定 `tag_admin` 與 `member` 角色的具體權限範圍
- **標籤管理者 `tag_admin`**：權限範圍由專案擁有者設定，可配置的權限包含：
  - 管理所屬成員標籤的設定（如 `externalTaskCreation`、記憶等）
  - 管理所屬成員標籤下的任務模板（建立、編輯、刪除）
  - 查看所屬成員標籤下的所有任務（即使非參與人）
  - 將成員加入或移出所屬成員標籤
  - 每個成員標籤可指定一或多位標籤管理者
- **專案成員 `member`**：權限範圍由專案擁有者設定，可配置的權限包含：
  - 建立任務（從自身標籤的任務模板）
  - 查看自身參與的任務
  - 在任務對話中操作（留言、確認 AI 建議、使用執行工具）
  - 瀏覽記憶

> **權限設定原則：** 專案擁有者透過 `permissionSettings` 統一設定各角色的權限範圍。`tag_admin` 與 `member` 的每項權限皆可獨立啟用或停用，提供彈性的權限控管。

> **權限衝突解決：** 一個成員可擁有多個成員標籤，當不同標籤的權限設定衝突時（如標籤 A 允許某操作、標籤 B 禁止），以**禁止優先（deny-first）**原則處理：只要任一標籤禁止該操作，該成員即無法執行。

#### 加入成員流程

專案擁有者與標籤管理者可透過 Email 加入成員。被邀請者須為同組織成員（或同時邀請加入組織）：
- **已有帳號且在組織中**：直接加入專案並指派成員標籤
- **已有帳號但不在組織中**：同時邀請加入組織與專案
- **尚無帳號**：系統發送邀請信至該 Email，收件者點擊連結後註冊帳號（Passkey 或 Email Magic Link），完成後自動加入組織與專案並獲得指定的成員標籤

#### 基於成員標籤的可見性與存取控制

以專案為單位，可設定每個成員標籤的權限範圍：

- **任務模板可見性**：成員可使用其所屬成員標籤擁有的任務模板。跨組建立任務則由各成員標籤的 `externalTaskCreation` 設定控管
- **任務可見性 `taskVisibility`**：成員可查看與操作自己作為參與人（`participants`）的任務。專案擁有者可看到全部任務
- **執行工具權限 `toolPermissions`**：哪些成員標籤能使用哪些工具
- **記憶可見性 `memoryVisibility`**：哪些成員標籤可以瀏覽哪些層級的記憶
- **資料表存取 `dataAccess`**：哪些成員標籤可以查看跨任務聚合的資料表

#### AI 操作權限

- AI 的每個寫入動作都需要有對應權限的成員確認
- AI 查詢工具遵循當前操作成員的可見性範圍

### 安全

- API Key 等敏感資訊加密儲存
- 所有 AI 的 prompt 和回應都可供審查
- 執行工具的操作都有確認步驟，防止誤操作

## 六、COSCUP 場景完整流程示例

### 前置作業

1. **組織已存在**：「COSCUP」組織已建立，累積了跨屆共用的組織記憶與工具設定
2. **建立專案**：在「COSCUP」組織中，從去年「COSCUP 2025」專案複製建立「COSCUP 2026」，繼承成員標籤、任務模板、記憶、工具設定與權限設計。同時繼承組織層級的工具設定
3. **調整設定**：更新今年的工具 API Key（專案層級覆寫組織設定）、新增/修改成員標籤、調整權限設定
4. **邀請成員**：透過 Email 邀請組織成員加入專案，分配標籤（贊助組、資訊組等）。新成員同時加入組織與專案。成員依據標籤只能看到相關的任務模板與任務

### User Stories：贊助組 — 與贊助商聯絡

> 背景：贊助組成員小明負責聯絡 X 公司贊助事宜。任務模板「與贊助商保持聯絡」包含待辦事項模板（初次聯絡 → 寄送贊助方案 → 確認贊助意願 → 簽約與收款 → 發佈贊助商貼文），其中「發佈贊助商貼文」有子待辦（蒐集素材 → 請公關組發文 → 通知贊助商已發文）。資料表定義「贊助商資訊」包含公司名稱、聯絡人、Email、贊助方案、金額、狀態，以及貼文相關欄位（公司簡介、贊助方案重點、公司 Logo、宣傳文案）。

#### Story 1：建立任務與初始化

1. 小明從「與贊助商保持聯絡」模板建立任務，命名為「與 X 公司聯絡」
2. 系統自動從模板實例化 5 個待辦事項（初次聯絡、寄送贊助方案、確認贊助意願、簽約與收款、發佈贊助商貼文），其中「發佈贊助商貼文」含 3 個子待辦
3. 觸發 `task_created` → AI 生成建議組（SuggestionGroup）：
   - **建議 1**（`upsertDataEntry`）：建議填寫 X 公司的基本資料到資料表（公司名稱、聯絡人、Email）
   - **建議 2**（`smtp/sendEmail`）：根據記憶中的信件範本，生成初次聯絡信草稿，收件人為 X 公司聯絡人
4. 小明**採納**建議 1，資料表更新，對話中出現 `tool_execution` 區塊
5. 小明**修改後採納**建議 2，調整信件內容中的稱呼與措辭後發送
6. 系統寄出信件，對話中記錄完整的寄信結果
7. 小明覺得修改後的措辭比範本更好，手動建立記憶：「初次聯絡信建議使用較輕鬆的語氣，避免過於正式」→ 存入任務模板 `task_template` 層級記憶，未來同模板任務都能參考

#### Story 2：收到贊助商回信

1. X 公司聯絡人回覆 Email，表示有興趣了解贊助方案
2. 系統匹配寄件者 Email → 找到外部成員「X 公司聯絡人」→ 將信件內容以 `email_inbound` 類型訊息加入任務對話
3. 觸發 `message_sent` → AI 生成建議組：
   - **建議 1**（`updateTodo`）：建議標記「初次聯絡」待辦為完成
   - **建議 2**（`smtp/sendEmail`）：生成贊助方案信件草稿，附上贊助方案文件連結
   - **建議 3**（`upsertDataEntry`）：建議更新資料表狀態欄位為「已回覆，待寄方案」
4. 小明逐一審核，全部採納

#### Story 3：成員主動對話與協作

1. 小明在任務對話中留言：「X 公司希望客製化方案，@贊助組 大家覺得可以怎麼調整？」
2. 系統發送通知給贊助組所有成員
3. 贊助組組長回覆：「可以提供 A 方案的加價版，多一個攤位」
4. 觸發 `message_sent` → AI 讀取對話上下文與記憶，生成建議組：
   - **建議 1**（`smtp/sendEmail`）：草擬客製方案回覆信，內容包含 A 方案加價版與額外攤位說明，回覆與 X 公司的既有 Email Thread
   - **建議 2**（`upsertMemory`）：建議記錄「A 方案可提供加價版，增加一個攤位作為客製選項」→ 成員標籤 `member_tag`（贊助組）層級
5. 小明修改後採納建議 1，採納建議 2，信件寄出、記憶存入

#### Story 4：追蹤與提醒

1. 寄出客製方案後一週，X 公司未回覆
2. 提醒系統觸發 `todo_stale`（「確認贊助意願」待辦長時間未推進）
3. 小明收到 Web Push 通知
4. 小明進入任務對話，向 AI 請求建議：「幫我寫一封 follow-up 信」
5. AI 生成建議組：
   - **建議 1**（`smtp/sendEmail`）：生成禮貌的跟進信草稿，回覆與 X 公司的既有 Email Thread，引用客製方案內容
6. 小明採納，信件寄出
7. 小明手動建立記憶：「X 公司回覆週期較長，建議寄出方案一週後主動 follow-up」→ 存入任務 `task` 層級記憶，供此任務後續參考

#### Story 5：確認贊助與簽約

1. X 公司回信確認贊助 A 方案加價版
2. 訊息進入任務對話，觸發 AI 建議組：
   - **建議 1**（`updateTodo`）：標記「確認贊助意願」為完成
   - **建議 2**（`upsertDataEntry`）：更新資料表（贊助方案：A 方案加價版、金額：NT$150,000、狀態：已確認）
   - **建議 3**（`hackmd/createDocument`）：建立贊助合約共筆文件
   - **建議 4**（`smtp/sendEmail`）：生成合約確認信草稿，回覆與 X 公司的既有 Email Thread
3. 小明逐一審核並採納

#### Story 6：跨組協作 — 向 OCF 確認收款

1. X 公司聯絡人來信通知已完成匯款，信件進入任務對話
2. 觸發 `message_sent` → AI 生成建議組：
   - **建議 1**（`smtp/sendEmail`）：草擬寄給第三方財務單位 OCF 窗口的確認信，詢問是否收到 X 公司的匯款（NT$150,000），建立新的 Email Thread（收件者不同）
   - **建議 2**（`upsertDataEntry`）：更新資料表狀態為「已匯款，待確認」
3. 小明採納，信件寄出、資料表更新
5. OCF 窗口回信確認已收到款項，信件進入任務對話（OCF 窗口為 Contact，系統自動匹配或建立外部聯絡人身份）
6. 觸發 AI 建議組：
   - **建議 1**（`updateTodo`）：標記「簽約與收款」為完成
   - **建議 2**（`upsertDataEntry`）：更新資料表狀態為「已收款」
   - **建議 3**（`smtp/sendEmail`）：草擬感謝信寄給 X 公司，確認收款完成，回覆與 X 公司的既有 Email Thread
7. 小明逐一審核並採納
8. 觸發 AI 建議組：
   - **建議 1**（`upsertMemory`）：建議記錄「OCF 確認收款流程約需 3 個工作天」→ 成員標籤 `member_tag`（贊助組）層級，供所有贊助任務參考
9. 小明採納

#### Story 7：待辦事項不按順序 — 臨時支線

> 背景：在「與 X 公司聯絡」任務中，尚在「寄送贊助方案」階段，X 公司突然提出場地需求。

1. X 公司聯絡人來信：「我們有一批設備需要提前進場佈置，請問場地什麼時候可以進場？」，信件進入任務對話
2. 觸發 `message_sent` → AI 生成建議組：
   - **建議 1**（`createTodo`）：建立臨時待辦「確認 X 公司設備進場時間」，類型為 `ad_hoc`，作為「簽約與收款」的子待辦
   - **建議 2**（`smtp/sendEmail`）：草擬信件給場地組詢問進場時間（新的 Email Thread）
3. 小明採納建議 1，但認為場地問題應該直接問場地組的人，**修改後採納**建議 2，改為在對話中留言「@場地組 X 公司需要提前進場佈置，請問什麼時候可以？」
4. 場地組成員回覆進場時間
5. 觸發 AI 建議組：
   - **建議 1**（`smtp/sendEmail`）：草擬回覆 X 公司進場時間，回覆與 X 公司的既有 Email Thread
6. 小明採納，信件寄出，標記臨時待辦為完成
7. 觸發 AI 建議組：
   - **建議 1**（`upsertMemory`）：建議記錄「X 公司有設備進場需求，需提前協調場地」→ 任務 `task` 層級記憶
8. 小明採納，回到原本的「寄送贊助方案」待辦繼續處理，系統不強制線性流程

#### Story 8：蒐集貼文內容，跨組請公關組發文

> 背景：任務模板「與贊助商保持聯絡」的待辦事項模板中，「發佈贊助商貼文」是其中一個待辦項目，包含子待辦（蒐集素材、請公關組發文、通知贊助商已發文）。資料表定義中包含貼文相關欄位（公司簡介、贊助方案重點、公司 Logo、宣傳文案）。公關組的成員標籤已設定 `externalTaskCreation`：任務模板「社群貼文發佈」允許贊助組建立任務。

1. 小明開始處理「發佈贊助商貼文」待辦，在對話中留言：「開始準備 X 公司的贊助貼文」
2. 觸發 `message_sent` → AI 根據記憶（過去贊助商貼文經驗）生成建議組：
   - **建議 1**（`upsertDataEntry`）：建議填寫資料表的貼文相關欄位（公司簡介、贊助方案重點、Logo 連結）
3. 小明**修改後採納**，補充 X 公司提供的宣傳文案，標記子待辦「蒐集素材」為完成
4. 觸發 `todo_completed` → AI 生成建議組：
   - **建議 1**（`createTask`）：從公關組的「社群貼文發佈」任務模板建立新任務「發佈 X 公司贊助貼文」，關聯到子待辦「請公關組發文」
   - **建議 2**（`shareDataToTask`）：將公司簡介、贊助方案重點、Logo、宣傳文案等欄位資料複製到新建立的公關組任務
5. 小明採納，系統建立任務並與子待辦「請公關組發文」建立關聯（`linkedTask`），資料複製到公關組任務。公關組成員收到通知
6. 公關組成員小華在「發佈 X 公司贊助貼文」任務對話中作業，資料表中已有贊助組分享過來的素材資料（公司簡介、Logo 等）。完成發文後在對話中貼上貼文連結，標記待辦為完成
7. 關聯任務完成 → 小明的「與 X 公司聯絡」任務對話中自動收到 `system` 訊息：「關聯任務『發佈 X 公司贊助貼文』已完成」，觸發 AI 建議組：
   - **建議 1**（`smtp/sendEmail`）：草擬信件通知 X 公司貼文已上線，附上貼文連結，回覆與 X 公司的既有 Email Thread
   - **建議 2**（`updateTodo`）：標記子待辦「請公關組發文」為完成
8. 小明採納，信件寄出，標記子待辦「通知贊助商已發文」為完成
9. 「發佈贊助商貼文」的所有子待辦已完成，小明標記該待辦為完成

#### Story 9：任務完成與記憶累積

1. 所有待辦事項已完成，小明標記最後一個待辦事項為完成
2. 系統偵測所有待辦事項已完成，觸發 `todo_completed` → AI 從對話歷史中提取經驗，生成建議組：
   - **建議 1**（`upsertMemory`）：「X 公司偏好客製化方案，回覆週期約一週，follow-up 信件有效」→ 任務 `task` 層級（僅與 X 公司相關的經驗）
   - **建議 2**（`upsertMemory`）：「贊助貼文素材應包含公司簡介、方案重點、Logo，提前 3 天交給公關組」→ 任務模板 `task_template` 層級（所有贊助商聯絡任務通用的流程經驗）
   - **建議 3**（`upsertMemory`）：「大型贊助商常有客製方案需求，可準備加價版方案作為談判彈性」→ 成員標籤 `member_tag`（贊助組）層級（贊助組的通用策略知識）
   - **建議 4**（`upsertMemory`）：「贊助商設備進場需提前與場地組協調，建議在簽約階段就確認」→ 專案 `project` 層級（跨組協作的經驗，不限於贊助組）
   - **建議 5**（`upsertMemory`）：「與贊助商溝通時使用正式但友善的語氣效果最好」→ 組織 `organization` 層級（跨屆通用的組織文化經驗）
3. 小明審核：
   - 採納建議 1，補充「X 公司聯絡人偏好在週二回信」
   - 採納建議 2
   - **修改後採納**建議 3，補充「加價版方案建議預先準備 2~3 種組合」
   - 採納建議 4
   - 採納建議 5
4. 各記憶存入對應層級：
   - 任務 `task` 記憶：下次若再與 X 公司合作，AI 會參考此經驗
   - 任務模板 `task_template` 記憶：所有「與贊助商保持聯絡」任務都能參考
   - 成員標籤 `member_tag` 記憶：贊助組所有任務模板的 AI 建議都會納入
   - 專案 `project` 記憶：整個專案中所有組別都能參考
   - 組織 `organization` 記憶：所有屆別的所有專案都能參考，跨年累積的組織知識
5. 小明將任務標記為已完成

### 跨任務聚合視角

- 贊助組組長在任務模板「與贊助商保持聯絡」的資料表聚合頁面，可一覽所有贊助商的聯絡狀態、贊助方案與金額
- 外部系統透過 REST API 查詢資料表，自動更新官網贊助商列表
- 公關組可從資料表聚合頁面批次查看所有已確認贊助商的貼文素材與發文狀態
